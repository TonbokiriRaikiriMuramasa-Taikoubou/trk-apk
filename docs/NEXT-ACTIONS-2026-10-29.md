# trk! Android版：これから行えること

整理日：2026-10-29。これは実装予定・調査候補の一覧であり、未実施の項目を実装済みや合格とみなさない。現在地は [HANDOFF](HANDOFF.md)、レビュー対応の理由は [対応記録](MEDIA3-REVIEW-FOLLOWUP-2026-10-29.md)、実機の記録先は [チェック表](ANDROID-DEVICE-CHECKS.md)。Web／PWA、既存のWeb Audio・FX、ゲームと利用者データを守りながら段階的に進める。

レビュー依頼中：まず [PC版取り込みのレビュー依頼](REVIEW-REQUEST-UPSTREAM-2026-10-29.md) と返答を確認し、指摘の再現・優先度・データ保護を評価してから修正する。該当変更はPR #8後の未マージブランチ。

## 端末がなくても進められる作業

1. **イヤホン切断時の保護を設計・実装する（優先）**。Androidの `ACTION_AUDIO_BECOMING_NOISY` と受信機の登録／解除を調査し、通常再生、Web Audio逆再生、ゲーム、読込中の選曲・プレビュー、遅延した `play()` 完了の停止と再発音防止を一つの方針にまとめる。明示的な再開操作までの扱い、背景・PiP・Activity破棄、切断後の再接続と、将来のMedia3／Audio Focusとの二重処理を設計。先に非同期競合の回帰テストを追加し、Android側をビルド・エミュレーターで確認する。**暫定対策を実装**。Bridge稼働中に通知を受けたら通常／逆再生・シンセの停止と再発音抑止を試みる。押鍵中と離鍵済みのシンセ余韻は切断イベント時に即時disconnectするよう修正し、モックと実スクリプト連携で検査した。タイミング測定の最大20個・約10秒先までの予定音も、切断時に取り消し測定を中止する。ゲーム効果音・カウントダウン等はsourceを追跡し切断時に停止。FXの最終出力を切り離し、明示再開時に音声グラフを再構築する暫定対策を追加した。SE試聴の実際の操作は曲のガードを解除しない。再構築失敗時は再生ガードを再設定して画面に再試行を案内する。モック検査のみで、案内の表示・操作や音声品質・安定性は実機確認が必要。通知の到達、バックグラウンド停止・音声経路・物理出力は未確認。実機で出力切替を検証するまで、スピーカーへの漏れを防げると保証しない。
2. **renderer終了からの安全な復旧を設計・実装する（優先）**。CapacitorのWebViewListener、Activity・Bridge・pluginの所有関係と破棄を整理。死亡したWebViewを使い続けず、再生成の連続ループや二重破棄を防ぎ、保存データを消さず、自動で音を再開しない復旧手順・利用者向け表示を決める。API 26以上のテスト専用エミュレーターでrenderer異常終了を再現し、回転・通常終了・PiP・連続失敗も試験。**ネイティブ復旧画面と再起動後の自動再生抑止を試作**。安全に処理できないケースはAndroidに委ね、復旧成功と扱わない。実機・複数OSでの安全性やデータ保持は未検証。
3. **既存の回帰テストを補強する**。アンテナON/OFF、PiP待機・失敗・実際の開始と終了、曲読込・逆再生の中断、TV無音プレビュー、シンセ発音と長押し解除、Web／PWAとAndroid相当の差を検査。jsdomはイベント・状態の確認であり、本物の音声や端末表示の代わりにはならない。
4. **Media3段階Aの設計を具体化する**。[状態・命令・競合の設計案](MEDIA3-STAGE-A-DESIGN-2026-10-29.md)と、テスト専用の偽Bridge／偽Playerモデルを追加。タイムアウトだけではWeb側の消音を保証できない反例を確認した。テストAPK限定で実Media3 `SimpleBasePlayer` のplaceholder・保留中の状態更新・優先停止・古い応答をAPI 35エミュレーターで検査した。複数Futureを順次取り消す途中に同期リスナーが再入すると古い状態を読める反例がある。共有Future案も試したが、途中の状態表示が遅延し、先行リスナーの再入では古い状態を読める。意図を同期更新する別案でもpause直後の `isPlaying=false` が消音を意味しない反例が出た。API 35では、テスト専用MediaSession経由でもMedia3側の非再生・Android側のpauseと偽再生主体の状態が食い違った。模擬メディアキーではMedia3の通常previousが曲途中で現曲先頭へ戻り、前曲専用コマンドでは前曲へ移る違いを確認した。既存trkの選曲・シャッフル／リピートと、他コントローラーに公開するコマンドの互換性を検討すること。Futureの契約と状態の意味、実際に音声停止できない場合の制約、通知UI・外部コントローラー・サービスも検討すること。テスト初回CI失敗の原因は未特定で継続監視。製品runtimeにはMedia3を含まない。仕様・実装は確定しておらず、実通信・OSでの試作と検証が必要。再生主体をWebViewに残す場合の単一セッション・コマンド・曲ID・キュー・位置・エラーの同期、JS未応答やrenderer終了、セッション重複、foreground serviceの権限・通知・起動制限、Audio Focus、テスト方法を整理する。WebViewが停止すれば橋渡しだけで音が継続しないことを前提とし、FX・解析・ゲームを維持。導入には依存物のライセンス／NOTICEと安全な失敗時の動作の確認が必要。Media3は**未導入**。
5. **取り込みと配布の設計を進める**。SAF・共有インテント・永続URIとアクセス失効時の再接続、IndexedDBとの関係を調べる。自動バックアップ除外・手動書き出しを維持。別途、署名鍵、アプリID、GPL・素材・推移依存のライセンス／NOTICEを整理する。現在の取り込みUIを根拠なく削除しない。
6. **CIの維持**。`npm run check`、`npm run cap:sync`、debug APKビルドと必要なAPI 35エミュレーターを実行し、失敗の原因・対象コミットを記録する。CIのdebug鍵は固定されていないため、別ビルドの上書きは失敗し得る。既存データ削除を回避し、更新前にバックアップを確認。公開用鍵やSecretsをGitへ入れない。

## 利用者と後で決めること

- アプリ／プロセス終了後に再生を復元・自動再開するか。復旧時に勝手に音を出さない現方針と区別する。
- 正式なアプリID、署名鍵管理と公開先・配布方法、ゲーム中の向き、東方素材を含まない構成の要否、同梱docsの削減。
- 消音のまま進める「謎設定」は、MIDI・Web Audioまで含む消音と復帰の安全な仕様・実機結果を見てから判断する。
